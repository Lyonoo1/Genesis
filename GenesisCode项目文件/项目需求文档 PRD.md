# DevAgent 项目计划书

> 项目代号:Genesis Code | 定位:通用AI助手平台(基础对话 + Skill/MCP + 应用市场) | 版本:v2.0

---

## 一、项目目的

个人学习型项目,优先级排序:

1. **系统学习AI/Agent开发**——亲手实现 tool calling、RAG、Skill/MCP插件协议、工作流状态机
2. **作为跳槽/转型面试作品集**——要求有技术深度,经得起面试官追问原理
3. **自己部署上线自用**——公网可访问,只服务自己,不做多用户商业化

**判断标准**:任何功能/技术选型,先问"能不能在面试里讲清楚原理",而不是"像不像真实企业产品"。

---

## 二、产品定位(v2.0 修正)

> **DevAgent 本身是一个通用AI助手平台**,和 Claude.ai / Codex 客户端同一层级——支持多会话对话、可下载安装 Skill、可作为 MCP client 连接外部或自建的 MCP server、有应用市场。

**关键修正**:此前 v1.0 把"需求→PRD→开发→Review→测试"这套软件研发工作流当作产品的核心功能,这是错误的。正确关系是:

```
DevAgent(通用平台:对话 + MCP client + Skill系统 + 应用市场 + 基础助手能力)
   └── Skill包:研发流程助手(需求/计划/PRD/开发/Review/测试)
   └── Skill包/MCP连接器:未来其他业务领域的扩展(待后续设计)
```

平台本身不内置任何具体业务流程,所有业务能力都以 **Skill 包**或 **MCP 连接器**的形式安装到平台上运行。"研发流程助手"只是第一个、也是验证平台可扩展性的旗舰 Skill 包。

### Skill 与 MCP 的区别(不能用同一套设计)

| | MCP | Skill |
|---|---|---|
| 本质 | 结构化工具调用协议,server暴露tools,带input/output schema | 指令/知识包(说明文档 + 可选脚本资源) |
| 来源 | 外部现成MCP server + 自己开发的MCP server | 用户下载安装,或自己开发上传 |
| 调用方式 | 模型按schema主动调用 | AI自动判断相关性加载,或用户在对话中用`/`手动指定 |

## 三、范围声明

### 明确要做

- 单人部署的Web应用
- 完整的通用对话平台:多会话管理、流式输出、markdown渲染
- Skill 系统:manifest 设计参考 MCP,支持`/`手动指定和AI自动触发
- MCP Client:能连接外部现成MCP server,也能连接自己开发的
- 应用市场:发现/已安装/我的开发三个视图,分类筛选,详情页含权限声明
- 外观与个性化设置:主题、字体、字号、对话密度
- 用量/成本仪表盘
- 命令面板(Cmd/Ctrl+K)、常用指令模板、对话产出物导出
- 第一个旗舰Skill包:研发流程助手(内部实现工作流状态机、代码RAG、Agent Loop、diff生成)
- 基础登录墙 + 轻量沙箱(资源限制的子进程执行)

### 明确不做(除非后期有余力)

- 多用户注册/多租户系统
- Skill/MCP的真实多人审核发布流程、评分评论系统、付费结算
- 企业级权限体系(RBAC、SSO)
- Docker 容器级插件隔离(留作后期可选加分项)
- 跨会话长期记忆系统(基础对话能力完整即可,不做长期记忆)

## 四、技术架构

### 4.1 整体分层

```
用户前端(对话 + 会话管理 + 应用市场UI + 设置)
        ↓
Skill 引擎 + MCP Client(平台核心能力层)
        ↓
Agent 运行时(处理tool calling、Agent Loop)
        ↓
已安装的 Skill / 已连接的 MCP Server
        ↓
知识库(向量索引,供具体Skill如"研发流程助手"使用)
```

### 4.2 技术选型

| 层 | 技术 | 备注 |
|---|---|---|
| 前端 | Next.js,部署于 Vercel | 对接流式响应,做会话列表、市场UI、设置面板 |
| 后端 | Python + FastAPI,部署于 Railway/Render | 异步支持好,和 Anthropic/OpenAI SDK 配合顺畅 |
| 数据库 + 向量库 | Supabase(Postgres + pgvector) | 自带 Auth,省去自建登录系统的时间 |
| LLM 调用 | 直接用官方 SDK,不用 LangChain | 先吃透底层 tool calling 原理 |
| 插件沙箱 | 早期:Python subprocess + 资源限制 | 后期可选升级 Docker(Fly.io） |
| 工作流状态机 | xstate 或轻量自定义(用于"研发流程助手"这个Skill内部) | 不属于平台核心,是Skill内部实现细节 |
| 登录 | Supabase Auth(单账号) | 防止公网URL被滥用消耗API额度 |

## 五、核心模块详细设计(含UI交互)

### 5.1 会话管理(左侧栏)

- **新建对话**:开启全新空白会话,不继承上一个会话的Skill/MCP配置
- **历史会话列表**:按时间分组(今天/3天前/更早),标题自动摘要生成,若会话有激活的Skill会在标题下方显示小标签
- **搜索**:关键词过滤历史会话标题与内容
- **会话操作**:重命名、置顶、删除

### 5.2 对话主界面

- **消息渲染**:用户消息右对齐气泡;AI回复左对齐、无气泡背景、支持markdown(代码高亮、表格)
- **流式输出**:逐字流式显示,过程中可点击"停止生成"
- **消息操作**(悬停出现):复制、重新生成、点赞/点踩
- **编辑重发**:点击自己发送过的消息可修改后重发,截断后续对话分支

### 5.3 Skill 系统

Manifest 示例(参考 MCP 设计思路):

```json
{
  "name": "unit-test-generator",
  "version": "1.0.0",
  "entry": "index.py",
  "permissions": ["read:file", "exec:sandbox"],
  "input_schema": { "type": "object", "properties": { "file_path": { "type": "string" } } },
  "output_schema": { "type": "object", "properties": { "test_code": { "type": "string" } } }
}
```

- **对话内指定**:输入框输入`/`唤出Skill列表,选中后变成chip贴在输入框,本次消息带上该Skill上下文
- **自动触发**:未手动指定时,AI根据描述自动判断是否调用已安装Skill,调用后在回复上方标注"使用了xx Skill"
- **已安装管理**:设置里列出所有已装Skill,可开关"是否允许自动触发"

### 5.4 MCP Client

- **连接管理页**(设置内):列表形式,"添加MCP Server"支持本地命令或远程URL两种连接方式
- 每个Server展示其暴露的tool列表(名称+简述),支持单个tool开关
- **对话内生效范围**:每个会话可选择本次启用哪些已连接的MCP Server,避免每次对话都带上全部工具定义浪费token

### 5.5 应用市场(详细布局)

**三个Tab**:
- **发现**:浏览可安装的Skill/MCP连接器
- **已安装**:管理已装项,可卸载、调整自动触发开关
- **我的开发**:自己上传的插件,状态显示"仅自己可见"(个人项目不做真实审核发布流程,但保留概念方便扩展)

**发现页结构**:
- 顶部搜索框
- 分类筛选(研发流程 / 效率工具 / MCP连接器,分类可扩展,不写死)
- 排序方式(最近更新 / 名称)
- 卡片网格:图标 + 名称 + 一句话简介 + 类型标签(Skill/MCP用不同颜色区分)+ 操作按钮(Skill显示"安装",MCP显示"连接",因为MCP通常需要额外填连接参数)

**详情页**(点击卡片进入):
- 完整说明(渲染README)
- 版本历史与更新日志
- **权限声明**:能执行代码/访问文件的Skill需像手机App权限提示一样列出申请的权限(`exec:sandbox`、`read:file`等)——这是安全设计,不是噱头
- 安装/卸载按钮 + "设为自动触发"开关

**我的开发页**:提供"上传新Skill"入口——上传manifest.json + 代码包,本地校验格式,上传后进入该列表,状态为未发布/仅自己可见

### 5.6 外观与个性化设置

- **主题**:浅色 / 深色 / 跟随系统
- **回复正文字体**:无衬线 / 衬线两个选项(参考Claude的设计语言——AI回复用衬线字体,与界面其他部分的无衬线字体区分开,让人一眼分清"这是AI在说话"还是"系统UI")
- **字号**:三档,只影响正文,界面控件字号不变
- **对话密度**:紧凑(消息间距小,适合调试时快速翻看)/ 舒适(间距大,更像常规聊天软件)

### 5.7 用量与成本仪表盘

设置内单独页面,展示:
- 本月Token消耗
- 预估费用
- 按Skill/对话维度的消耗排行(哪个Skill最耗token一目了然)

这个模块直接对应"公网部署后API费用失控"的风险,不能只依赖后台Budget Alert,产品内必须有可视化面板。

### 5.8 效率功能

- **命令面板**(Cmd/Ctrl+K):全局快捷键呼出,可快速新建对话、切换Skill、跳转设置,键盘优先交互是这类工具型产品(Codex、Cursor)的标配
- **常用指令模板**:高频用的prompt可保存为快捷指令,和Skill选择器共用`/`触发机制
- **对话/产出物导出**:PRD、代码diff等产出物一键导出为Markdown文件

### 5.9 旗舰Skill包:研发流程助手(平台之上的第一个应用)

这是运行在DevAgent平台上的一个Skill包,内部自行管理以下逻辑(不属于平台核心,是这个Skill的实现细节):

- **工作流状态机**:需求录入 → 需求分析 → 计划拆解 → PRD生成 → 技术方案 → 开发(生成diff)→ Code Review → 单元测试,阶段间需人工确认卡点
- **代码RAG**:对接入的Git仓库做分块+embedding+检索
- **Agent Loop**:任务规划→调用工具→生成代码diff→人工确认→应用,需设最大步数上限防止死循环

## 六、路线图(业余时间,每周几小时,长期迭代,预期总周期12-18个月)

| 阶段 | 时间 | 目标 | 产出 |
|---|---|---|---|
| 1 | 第1-2月 | 基础对话平台上线 | Next.js(Vercel)+ FastAPI(Railway)+ 登录墙 + 多会话管理 + 流式对话 + 基础外观设置,已部署可访问 |
| 2 | 第3-4月 | Skill机制 + MCP Client核心 | manifest格式定稿,`/`Skill选择器,MCP连接管理页,先硬编码2-3个能力验证整套机制 |
| 3 | 第5-6月 | 应用市场UI打通 | 发现/已安装/我的开发三个视图,分类筛选,详情页与权限声明,安装/卸载全流程跑通 |
| 4 | 第7-9月 | 旗舰Skill包:研发流程助手 | 工作流状态机 + 代码RAG(pgvector)+ Agent Loop + diff生成,作为平台可扩展性的完整案例。**此节点可作为面试Demo** |
| 5 | 第10-12月 | 体验打磨 | 用量仪表盘、命令面板、常用指令模板、导出功能 |
| 6 | 第12月+ | 沙箱升级 + 更多Skill(可选) | 硬编码能力改为可插拔Skill;时间充裕再上Docker沙箱隔离;后续可设计其他业务方向的Skill包 |

**执行原则**:每个阶段结束保持"可演示"状态,不在半成品长期搁置。

## 七、风险与应对

| 风险 | 应对 |
|---|---|
| 范围蔓延 | 严格对照第三节"明确不做"清单 |
| 业余时间不稳定,项目停滞 | 阶段拆得足够小,保证阶段成果随时可演示 |
| 部署后API费用失控 | 第一阶段做登录墙 + Budget Alert;第10-12月补上用量仪表盘可视化 |
| 学了很多但讲不清楚原理 | 每阶段完成后用3-5句话向假想面试官解释"这一步怎么做的、为什么这样设计" |

## 八、面试话术要点(项目完成后回填)

- DevAgent的平台/应用分层是怎么设计的?为什么把研发流程做成Skill而不是内置功能?
- Skill和MCP两套机制的区别是什么,为什么不能用同一套manifest?
- 插件系统的manifest设计参考了什么(MCP),解决了什么问题?
- RAG里chunking怎么做的?召回不准时怎么调?
- Agent Loop怎么防止无限循环/失控调用工具?
- 为什么代码修改用diff+人工确认,而不是AI直接改文件?
- 部署后怎么做成本控制(用量仪表盘 + Budget Alert)和安全防护(权限声明 + 沙箱)?
